## ۲. ذخیره‌سازی، رضایت، حذف و حریم خصوصی (همه سمت کلاینت)
هیچ مسیر نوشتن در سرور وجود ندارد (تست ایستا: `no-writes.test.ts`؛ فقط `GET`، اتصال DB فقط‌خواندنی). شناسه‌ی ماموریت ۱۲۸ بیتی تصادفی (`msn_` + ۳۲ هگز، `crypto.getRandomValues`) و به‌تنهایی چیزی را باز نمی‌کند: سرور ماموریتی ندارد.
| جایگاه | کجا | چه زمانی | ماندگاری |
|---|---|---|---|
| **TAB** (پیش‌فرض) | `sessionStorage` | هر ماموریت جدید | تا بستن تب؛ برچسب «موقت — فقط همین تب» |
| **DEVICE** | IndexedDB (`hamghadam-missions`) | **فقط** با دکمه‌ی «ذخیره روی این دستگاه» | همین مرورگر/پروفایل؛ بین دستگاه‌ها هم‌گام نمی‌شود |
| **MEMORY** | حافظه‌ی صفحه | وقتی هر دو بسته‌اند | تا بستن صفحه؛ شناسه‌های غیرحساس در URL می‌ماند تا refresh بازسازی کند |
* ذخیره‌ی یادداشت‌ها نیازمند تیک رضایت جدا؛ بدون آن، در نسخه‌ی IndexedDB `notes:null`.
* «حذف از این دستگاه»، «حذف کامل ماموریت» و «حذف همه» (تب + دستگاه + پیش‌نویس‌های موقت `hamghadam.inquiry.*`/`hamghadam.agent.*`) با تأیید.
* **ذخیره نمی‌شود:** GPS دقیق (فقط نام محله‌ی preset)، شماره‌ی تلفن، هر پاسخ شبیه‌سازی‌شده، کلید/رمز، زنجیره‌ی تفکر. طرح `strict` است و فیلد اضافه رد می‌شود.
* اعتبارسنجی سخت هنگام بارگذاری (`parseMission`، zod): نسخه‌ی ناسازگار/خراب/id ناهمخوان = «قابل‌خواندن نیست» و قابل‌حذف؛ هرگز «ترمیم و اعتماد» نمی‌شود. پاسخ‌های DEMO داخل inquiry دور ریخته می‌شوند. `rev` و compare-and-set (در یک تراکنش IndexedDB) از lost update بین دو تب جلوگیری می‌کند؛ نوبت نوشتن FIFO است.
* quota / حالت خصوصی / دسترسی رد‌شده: اعلام صادقانه + ادامه از حافظه؛ جریان خرید متوقف نمی‌شود.

## ۳. ماشین حالت و قراردادهای بازاستفاده‌شده
* `src/domain/mission.ts`: `ShoppingMissionV1`، `missionReducer` (خالص، بدون ساعت/شبکه)، `CHECKLIST`، `readiness`، `triggersOf`، `missionPhase`، `exportChecklistText`، `summarizeMissionForAgent`.
* **بازاستفاده:** `InquiryState` و `inquiryReducer` فاز ۶ دست‌نخورده (فقط `USER_REPORTED` وارد می‌شود)؛ `deriveOutcome`، `resolveInquiryContext`، `compareSellersForProduct`، `findSellersForProduct`، `recommendShoppingAreas`، `adviseProducts`، `evaluateHours`؛ `MissionState`‌های فاز ۱ از `legacyStateOf(phase)` (هم‌خوان با `missionStateFor`).
* مرحله (phase) **مشتق** است نه ذخیره‌شده: نیاز → محصول → فروشنده → پرسش → منتظر پاسخ شما → پاسخ ثبت‌شده → آماده مراجعه → پایان/رها.
* **ناوردها:** فروشنده بدون محصول رد می‌شود؛ تغییر محصول/نسخه، فروشنده‌ی وابسته/inquiry/shortlist را کنار می‌گذارد ولی نیاز/بودجه/محله/زمان را نگه می‌دارد؛ تیک‌ها به `محصول|نسخه|فروشگاه|پیشنهاد(|زمان)` گره خورده‌اند (برای فروشنده‌ی دیگر شمرده نمی‌شوند ولی پاک هم نمی‌شوند؛ تغییر فقط زمان، فقط بررسی ساعت را باز می‌کند)؛ «نتیجه‌ی پرسش» با تیک دستی `done` نمی‌شود، فقط با پاسخ ثبت‌شده‌ی کاربر یا رد صریح؛ `MARK_VISITED` فقط با `ready` تازه.
* **آمادگی** = بررسی‌های لازم مرور شده + فروشگاه + زمان صریح + بدون محرک مسدودکننده. هرگز «موجودی تأییدشده» نیست و همین جمله روی UI و فهرست خروجی هست.
* خط زمانی: هر رویداد مهم با برچسب منشأ (`DATASET_RECORDED`/`USER_REPORTED`/`USER_ACTION`/`SYSTEM`؛ **DEMO_SIMULATED عضو نیست**)، زمان، `rev` و «گام بعد».

## ۴. سه ماموریت قابل‌تکرار روی داده‌ی واقعی
شناسه‌ها: محصول Dahua `product_7308febc43c2f793fd0e1cf9`، نسخه `unknown|HDW1200CLQP`، فروشگاه `shop_8670c71ca3baff62d68de422`، پیشنهاد `offer_742932354aecd83d7fc7c266` (قیمت ثبت‌شده ۴٬۱۰۰٬۰۰۰ تومان؛ ساعت اعلام‌شده ۰۹:۰۰–۲۰:۰۰، برای روزهای ۲۰۲۶‑۱۰‑۲۴ تا ۲۰۲۶‑۱۰‑۲۹ با داده راستی‌آزمایی شد). e2e: `e2e/missions.spec.ts`.
1. **پرسش دستی → پاسخ کاربر → فهرست آمادگی:** `/missions/new?...` ← «ساخت ماموریت» ← تب پرسش: کپی، «خودم پرسیدم»، ثبت پاسخ (موجود/همین مدل/۴٬۱۰۰٬۰۰۰) ⇒ `USER_REPORTED` ← تب مراجعه: ۴ بررسی + «نتیجه‌ی پرسش» مشتق ⇒ `آماده مراجعه` + جمله‌ی «به معنی موجودی تأییدشده نیست»؛ کپی فهرست بدون تلفن/DEMO؛ سپس «مراجعه انجام شد».
2. **ناموجود/بدون پاسخ → جایگزین واقعی یا منطقه:** «فروشنده گفت موجود نیست» ⇒ ≥۱ فروشگاه جایگزین با `offerId` که در DB به همان محصول و فروشگاه تعلق دارد، سطح هویت A/B، trade-off (قیمت ثبت‌شده، فاصله‌ی خط مستقیم، ساعت)؛ انتخاب آن فقط بررسی‌های وابسته به فروشنده‌ی قبلی را از شمارش می‌اندازد. برای محصول تک‌پیشنهادی همان دسته: کارت‌های منطقه با منبع/تاریخ/نوع و نشان «فروشنده نیست».
3. **تغییر قیمت:** بودجه ۴٬۵۰۰٬۰۰۰ + گزارش کاربر ۴٬۹۰۰٬۰۰۰ ⇒ ثبت‌شده ۴٬۱۰۰٬۰۰۰ / گزارش ۴٬۹۰۰٬۰۰۰ / اختلاف ۸۰۰٬۰۰۰ / «۴۰۰٬۰۰۰ از سقف بودجه بیشتر می‌شود»؛ قیمت DB دست‌نخورده (قبل/بعد از reload)؛ لینک بازکردن مقایسه با همان فیلترها.

## ۵. رفتار در حالت‌های دشوار
| حالت | رفتار |
|---|---|
| قیمتی که فروشنده گفت | فقط `USER_REPORTED`، سناریوی بودجه؛ `offers_raw`/رتبه‌بندی عوض نمی‌شود |
| ساعت نامعلوم | هشدار «نامعلوم؛ بسته حساب نشده»، مانع آمادگی نیست؛ هرگز «باز» |
| خارج از ساعت | مسدودکننده + کنترل «مرور شد» غیرفعال + نخستین بازه‌ی **اعلام‌شده**‌ی بعدی (در غیر این صورت حدس نمی‌زنیم؛ تعطیلات رسمی محاسبه نمی‌شود) |
| قیمت ثبت‌نشده | «قیمتی ثبت نشده — نیازمند استعلام» |
| مدل/واحد دیگر | `WRONG_MODEL` تأیید «همین کالا» را مسدود می‌کند؛ نسخه‌های دیگر فقط لینک به صفحه‌ی محصول (خودکار جایگزین نمی‌شود) |
| خارج از پوشش | جمله‌ی «در نمونه‌ی داده نیست ≠ در تهران نیست» + مناطق خرید |
| شناسه‌های ناهمخوان (جعلی/کهنه) | `facts-mismatch`؛ هیچ واقعیتی نمایش داده نمی‌شود |
| دریافت داده ناموفق/آفلاین | پیام صریح؛ ساعت «بسته یا باز فرض نمی‌شود» |

## ۸. امنیت
شناسه‌ی بدشکل ۴۰۴؛ id درست ولی ناشناخته «روی این دستگاه نیست»؛ رکورد مسموم (phone/gps/نسخه‌ی آینده) خوانده نمی‌شود؛ ماموریت‌ها هم‌دیگر را نمی‌بینند؛ رقابت (کلیک‌های سریع، دوبل‌کلیک، دو تب) بدون lost update؛ حالت شبیه‌سازی: نه rev تغییر می‌کند، نه storage/IndexedDB/خروجی/URL؛ بعد reload ناپدید؛ هیچ درخواست غیر‌GET یا میزبان بیرونی؛ هیچ `tel:`/`09…` در HTML. اجرای مأموریت از دستیار: فقط شناسه/بودجه/محله seed می‌شود؛ هیچ پاسخ/شاهدی نه.

## ۹. شواهد rubric (بدون امتیاز)
محصول: جریان پس از انتخاب فروشنده ✅ (mock/داده واقعی). UX: موبایل تب‌دار، axe ✅ (صفحه‌خوان ⬜). هوشمندی: بازیابی قطعی با شناسه‌ی واقعی ✅؛ مدل زنده ⬜. استقرار: Docker محلی ✅؛ بیرونی ⬜. فنی: reducer خالص، compare-and-set، تست ایستای نبود‌نوشتن ✅. داده: DB دست‌نخورده ✅.

## ۱۰. NOT VERIFIED و گیت پس از فاز ۸
`LLM NOT LIVE VERIFIED`، `EXTERNAL LIVE RETRIEVAL NOT VERIFIED` (رجیستری خالی). گیت جدا: (الف) tool-calling زنده با بودجه‌ی تأییدشده‌ی مالک و ارزیابی `npm run agent:eval` با ارائه‌دهنده‌ی زنده؛ (ب) ≥۱ منبع مجاز با تطبیق دقیق مدل، اسکرین‌شات/ارجاع و سیاست منبع. تا آن موقع علامت نمی‌خورند. Summary فقط‌خواندنی `summarizeMissionForAgent` برای استفاده‌ی آینده آماده است (مدل راه نوشتن ندارد).

## ۱۱. ریسک‌ها و وابستگی فاز ۹
نمی‌توان ماموریت را روی دستگاه دیگر دید (طراحی)؛ IndexedDB با پاک‌کردن داده‌ی مرورگر از بین می‌رود؛ فقط Chrome آزموده شد؛ تعطیلات رسمی در ساعت‌ها نیست؛ ریاضی فاصله‌ها خط مستقیم است؛ فهرست چندکالایی (P1) و تحلیل چندمرورگری/صفحه‌خوان و بازسازی بصری صفحه‌ی `/missions/new` برای فاز ۹.
