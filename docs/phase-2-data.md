## ۲. تصمیم‌های فنی
- **`node:sqlite` (SQLite داخلی Node 24)، نه `better-sqlite3`.** دلیل: هیچ افزونه‌ی بومی برای کامپایل/حمل نیست (image فقط runtime Node می‌خواهد)، FTS5 و R-Tree و توابع ریاضی در همین نسخه تأیید شد (`sqlite_compileoption_used`). *هزینه:* ماژول هنوز «آزمایشی» چاپ می‌کند و API جوان‌تر است؛ ورژن Node باید ≥ 22.5 (ما 24) و SQLite میزبان/کانتینر ممکن است اندکی فرق کند (۳٫۵۳٫۳ در برابر ۳٫۵۳٫۴؛ فایل سازگار است).
- **CSV:** `csv-parse` (استریمی، فیلدهای چندخطی — ۱٬۰۱۳ محصول و ۱۵٬۴۵۵ offer دارای newline داخل کوتیشن‌اند). **ZIP:** `yauzl` (استریمی؛ رد مسیرهای `../` و مطلق خودش و من؛ فقط نام دقیق `[dir/]{products,offers,shops}.csv`؛ `__MACOSX/` نادیده؛ نام تکراری = خطا؛ سقف اندازه). هیچ‌چیز روی دیسک استخراج نمی‌شود و بایت‌های منبع تغییر نمی‌کنند.
- **`tsx`** فقط برای اجرای اسکریپت‌های TypeScript (alias `@/` را هم می‌فهمد).
- **بازسازی کامل در فایل staging + swap اتمیک** (ساده‌تر و ایمن‌تر از به‌روزرسانی درجا): idempotency و crash-safety بدون منطق upsert پیچیده.
- **ایندکس FTS بدون‌محتوا** (`content=''`) برای صرفه‌جویی حجم؛ نتایج از `products` با rowid خوانده می‌شوند.
- **قیمت‌های > 2⁵³−۱:** `node:sqlite` هنگام *خواندن* عدد صحیح بزرگ‌تر از 2⁵³ خطا می‌دهد (در fixture کشف شد). بنابراین رقم‌های دقیق در `price_toman_raw` می‌مانند، ستون عددی NULL و `price_out_of_range=1` + پرچم `PRICE_ABSURD_MAGNITUDE` ثبت می‌شود.

## ۳. چرخه‌ی واردسازی و ایمنی
1. staging: `data/app.sqlite.importing-<pid>` (`journal_mode=MEMORY`، `synchronous=OFF`؛ یکبارمصرف) ← مهاجرت ← `products` ← `shops` ← `offers` (دسته‌های ۵۰۰۰ تایی).
2. مشتقات: شمارنده‌ها، FTS5، R-Tree (SQL مجموعه‌ای).
3. پرچم‌ها (`computeFlags`): SQL مجموعه‌ای + عبور «کوچه‌ای» روی محصولات با keyset-pagination (حافظه‌ی کراندار).
4. **دروازه‌ی صحت:** شمارش خوانده‌شده = ذخیره‌شده؛ ۰ یتیم (مگر `--allow-orphans`)؛ FTS و R-Tree هم‌شمار؛ `quick_check`. شکست = **پایگاه زنده دست‌نخورده**.
5. `ANALYZE`، بستن، `fsync`، `rename` اتمیک، `fsync` پوشه.
6. SIGINT/SIGTERM staging را پاک می‌کند؛ ماندهٔ `kill -9` در اجرای بعدی (pid مرده) پاک می‌شود.

### دقت پرچم مدل (نمونه‌ی دستی، نه benchmark)
در نخستین طراحی (کلید مدل ساده) از نمونه‌ی ۲۴تایی فقط حدود ۱۴ مورد واقعاً «نسخه‌ی دیگر» بود. نمونه‌برداری مشکلات را نشان داد: فاصله‌ی داخل مدل (`FTP 4E-200S`)، پیشوند اندازه (`43XH600`)، اندازه‌ها (`25V-1.5A-1W`, `200dpi`) و کلمه+عدد (`Necklace5`). اصلاح: کلیدها دقیق‌تر شد و پرچم **دو سطح** شد: *MISMATCH* فقط برای «هم‌خانواده با اختلاف کم» (فاصله‌ی ویرایش ≤۳، نسبت ≤۰٫۳۴، شروع یکسان؛ مثل `GV3P60/GV3P65`، `Hot 10/Hot 11`)؛ بقیه *UNCONFIRMED* و غیرمسدودکننده. **اصلاح (فاز ۳):** برآورد اولیه‌ی «≈۱۷ از ۲۰» خوش‌بینانه بود. نمونه‌ی بزرگ‌تر و برچسب‌دار (۳۰ جفت MISMATCH، قضاوت دستی دستیار، با دسته‌ی «نامشخص») نشان داد: **۶۰٪ نسخه‌ی متفاوت، ۱۶٫۷٪ مثبت کاذب، ۲۳٫۳٪ نامشخص** (جزئیات و بقیه‌ی گروه‌ها در `docs/phase-3-evaluation.md`). مثبت کاذب شناخته‌شده: `3RW30` در برابر `3RW3028`؛ تایپی `PC-` در برابر `IPC-`.

## ۶. ساعت کاری (حقایق واقعی)
- ۴٬۴۷۲ فروشگاه برنامه‌ی قابل‌استفاده دارند؛ ۲٬۰۰۳ برابر `{}` و ۱ فروشگاه همه‌ی روزهایش «unsupported» (با ساعت ۱۱:۰۰–۱۱:۰۰) است. در داده‌ی واقعی **هیچ** شیفت شب‌گذر، «تا نیمه‌شب» یا روز declared فقط‌placeholder وجود ندارد (کد برای همه‌ی این‌ها نوشته و با fixture/واحد تست شد).
- `2026-10-21 11:00` تهران (چهارشنبه): باز ۴٬۳۱۳ · بسته ۱۵۴ · نامشخص ۲٬۰۰۹.
- هر ۲٬۰۰۴ فروشگاه بدون برنامه در ۳ زمان آزمون «نامشخص» بودند (هرگز «بسته» یا «باز»).

## ۸. مشاهده‌ی طرح پرس‌وجو (EXPLAIN QUERY PLAN)
- محصول با id، offerهای محصول (`idx_offers_product_shop`)، offerهای فروشگاه (`idx_offers_shop`)، پرچم‌های موجودیت (`idx_flags_entity`): همه `SEARCH … USING INDEX`.
- offerهای محصول با `ORDER BY source_row`: `USE TEMP B-TREE FOR ORDER BY` — روی چند ده سطر بی‌اهمیت؛ و `LIMIT` سخت ۲۰۰ دارد.
- FTS: `SCAN product_fts VIRTUAL TABLE INDEX 0:M5` سپس `SEARCH p USING INTEGER PRIMARY KEY` و temp B-tree برای مرتب‌سازی BM25: هزینه ∝ تعداد تطبیق‌ها (۱۰–۱۴ ms برای ۹–۱۳ هزار تطبیق).
- R-Tree: `SCAN g VIRTUAL TABLE INDEX 2:D0B1D2B3` (جست‌وجوی جعبه‌ای) سپس join با rowid.

## ۹. محدودیت‌ها و ریسک‌های باقی‌مانده
1. **FTS5 تصحیح غلط املایی فارسی نمی‌کند.** نرمال‌سازی (ی/ک/ارقام/نیم‌فاصله/اعراب) و پیشوند هست؛ ریشه‌یابی، مترادف و فاصله‌ی ویرایش برای فاز ۳ می‌ماند. کلمات بسیار رایج («و»، «با»، «از»…) و پرسش یک‌حرفی نتیجه‌ی بی‌ارزش می‌دهند؛ فاز ۳ باید حداقل طول/stop-word بگذارد.
2. **fallback «یا»** فقط وقتی «و» صفر نتیجه دارد و باید در UI «تطبیق ضعیف‌تر» برچسب بخورد (`strategy`).
3. **واحد قیمت از عنوان حدس زده می‌شود.** نمونه‌ی «سیم افشان ۲٫۵ خراسان» با قیمت ۳۹٬۰۰۰ تا ۱۱۰٬۰۰۰+ بدون برچسب واحد در عنوان است و اختلاف ≈ ۱۲× از آستانه‌ی ۲۰× کمتر است ⇒ **پرچم نمی‌خورد.** Phase 3 باید «پراکندگی قیمت همتایان» را هشدار دهد.
4. **کهنگی:** ۲۲٪ offerها بیش از ۹۰ روز از اسنپ‌شات عقب‌اند؛ مرجع، زمان داده است نه «اکنون».
5. **دقت پرچم مدل** نمونه‌ای است (بخش ۵) و مثبت کاذب دارد؛ پرچم هیچ‌گاه ردیف را حذف نمی‌کند.
6. `products` ۴۰۹ MiB به‌خاطر نگهداری خام + نرمال `specs`/`images`؛ اگر حجم مسئله شد می‌توان خام را فشرده کرد (نیازمند تصمیم درباره‌ی منشأ).
7. اثر انگشت `product_fts` فقط از `docsize` است (تعداد/طول سند)، نه محتوای توکن‌ها.
8. تعداد offer در رتبه‌بندی جست‌وجو دخالت ندارد.

## ۱۰. آمادگی برای فاز ۳ (جست‌وجو)
**آماده:** نرمال‌سازی مشترک ایندکس/کوئری، `buildMatchQuery` ضد‌تزریق، `searchProducts` (کراندار)، جست‌وجو بر اساس کلید مدل حتی از عنوان offer، `listOffersForProduct` با `comparisonEligible`/پرچم‌ها/مسافت، `shopsNear`، `evaluateDeclaredHours`.
**وابستگی‌ها / تصمیم‌های لازم از مالک:** آیا ارقام تعداد offer در رتبه‌بندی وارد شود؟ سیاست نمایش قیمت قدیمی/ناهمخوان؛ منبع موقعیت کاربر؛ مجموعه‌ی ارزیابی برچسب‌دار برای پرچم مدل؛ تأیید ساخت route handler های `/api/*` یا Server Components مستقیم.
